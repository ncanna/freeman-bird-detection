# H55 experiment — System One on a random video sample

Status: **complete** (2026-10-04)

> **Program context.** H55 is one of several site datasets (h23 annotated
> main, h03, H55, the 11-frame `train_images` pilot). The program goal is
> detection of the **Hume's Leaf Warbler** (*Phylloscopus humei*) — a
> ~10 cm cryptically plumaged warbler, small and occluded in standard
> camera-trap frames. The paper draft
> (`docs/paper/typed_decision_camera_trap_implementation.tex`) carries the
> full framing; this document is the H55 engineering record.

## Why

The h23 dataset has gold COCO boxes but the H55 download (`data/H55/`) is raw
camera-trap material we have never run the System One harness on. Before
planning an annotation effort, we want to know what the System One models say
about H55 frames and whether those answers are usable as pseudo-labels. This
experiment runs the full loop on a small, reproducible, random subsample:

> sample videos → extract frames → ask System One questions → map every frame's
> answers into **COCO format**.

Everything is scripted and seeded, so the sample and the frames can be
regenerated byte-for-byte (PNG encoding is deterministic per OpenCV version).

## Step 2 — video → frames

Tool: [`system_one_detector/tools/video_to_frames.py`](../tools/video_to_frames.py)

```bash
python3 -m system_one_detector.tools.video_to_frames \
    --sample-json data/H55/video_sample.json \
    --out-dir data/H55/frames_sample5_stride10 \
    --stride 10
```

- **Naming**: `<video_stem>_frame_<original_index:06d>.png` (h23-compatible;
  `system_one_detector.datasets.frames` groups them by video stem unchanged).
- **Stride 10** keeps every 10th frame of the source, original index 0 included.
  The original index — not a renumbered position — is in the filename, so any
  frame traces back to its exact position in the video.
- **Lossless PNG** (matches h23). cv2 5.0.0, 4 parallel workers.
- `frame_map.csv` (frame, video, original_index) and
  `extraction_provenance.json` are written into the frames dir.

**Result: 230 frames** (31 + 31 + 31 + 31 + 106), 535 MB.

At 29.97 fps, stride 10 ≈ 3 samples/second, which resolves bird motion without
writing every near-duplicate frame. For finer temporal coverage raise the
stride granularity and re-run; the tools, not the docs, are the source of truth
for whatever was actually extracted.

## Step 3 — System One runs

### 3b. Real run — Jev-Omni MLX 4-bit

The only pixel-seeing backend available on this machine without API keys
(Clef/Djev/TypeSafe need credentials; Jev-Omni CUDA needs an NVIDIA GPU). The
standalone MLX POC is used directly — see the "Local MLX proof of concept"

```bash
.venv-jevomni/bin/python system_one_detector/jev_omni_mlx_poc.py \
    --images data/H55/frames_sample5_stride10 \
    --no-browser \

```

Settings: 70 image tokens, temperature calibration from the checkpoint's
`calibration.json` (JevBench fit), same three questions. Prior POC on 11
frames measured 1.75 s median per question at 70 tokens → expected ~20 min for
230 × 3 questions. The POC serves a review web UI after writing its JSON
(stop it with ctrl-c; `--json` lands before the server starts).

Run record: `outputs/h55/poc_h55_70tok.json` (results below).

## Step 4 — per-frame results → COCO

Tool: [`system_one_detector/tools/coco_from_decisions.py`](../tools/coco_from_decisions.py)

```bash
python3 -m system_one_detector.tools.coco_from_decisions \
    --input outputs/h55/poc_h55_70tok.json \
    --frames-dir data/H55/frames_sample5_stride10 \
    --output outputs/h55/poc_h55_70tok_coco.json
```

Auto-detects engine `decisions.json` vs POC results JSON. Also writes
`per_frame_summary.csv` (one row per frame) next to the output.

### COCO mapping — what is invented and what is not

System One does not emit boxes, so the COCO file is honest about what the model
actually said:

- **images**: one entry per frame — `id`, `file_name`, `width`, `height`,
  `video_stem`, plus `attributes` carrying the raw answers. An entry with **no
  annotations means the model predicted no bird**.
- **annotations**: emitted only when
  1. `bird_present` probability ≥ `--noul-threshold` (default 0.5), **and**
  2. `largest_bird_cell` names one of the nine grid cells (not `none`).
- **bbox**: the predicted cell rectangle — a third of the frame width/height,
  positioned by the cell (t/m/b rows, l/c/r columns, top-left origin). This is
  a *location prior*, not a tight box. Cell semantics come from
  [`datasets/questions.py`](../datasets/questions.py); `cell_of_box` is the
  inverse mapping used to grade.
- **score**: the bird-present probability (the closest analogue of detector
  confidence for pycocotools-style consumers).
- **attributes** on each annotation keep everything else the model said:
  cell, cell confidence and full cell distribution, count level, count label,
  weighted count score, count distribution. Nothing is discarded by the mapping.
- **categories**: `[{id: 1, name: "bird", supercategory: "animal"}]`.
- **info.source**: input JSON path + sha256, input format, models, threshold,
  frame counts — provenance travels with the file.

Contradictory frames (bird present but cell `none`, or cell chosen but
bird-present below threshold) produce **no annotation** rather than a guessed
box; the raw answers remain in `images[].attributes` and the summary CSV.

## Results

Raw artifacts: `outputs/h55/` (paths in the table above). 230/230 frames
decided, **0 errors**, wall 1105.7 s (~18.4 min), median 1456.6 ms per question
at 70 image tokens, model load 10.3 s, peak 7.2 GB Metal memory.

### What the model said

| question | prediction | n | mean confidence |
| --- | --- | ---: | ---: |
| `bird_present` | No bird is visible | **230 / 230** | 0.897 |
| `bird_count` | no birds are visible | 230 / 230 | 0.853 |
| `largest_bird_cell` | middle-right 108 · top-left 55 · center 30 · middle-left 28 · top-center 9 | — | 0.280 |

- `bird_present` probability never reached 0.5 — **max 0.274**
  (`IMG_0572_frame_000700`), then 0.212, 0.208, 0.202, 0.199. The distribution
  is a long low tail: median ≈ 0.09, min 0.064.
- `largest_bird_cell` is asked unconditionally by the POC; with no bird
  predicted its 0.28 mean confidence and skewed spread are **noise, not
  locations** — ignore those columns in the summary CSV for this run.
- Cross-check with the earlier POC on `train_images`
  (`poc_results/jev_omni_mlx_train_images_70tok.json`): same shape — 11/11
  "No bird is visible" at ~0.91 confidence.

### COCO outputs

- `poc_h55_70tok_coco.json` — threshold 0.5: **230 images, 0 annotations.**
  Every image entry still carries the raw answers in `attributes`.
- `poc_h55_70tok_coco_t020.json` — sensitivity variant at threshold 0.2:
  230 images, **4 annotations** (cell-rect boxes for the four frames above).

### Interpretation (no gold labels — read as behaviour, not accuracy)

1. **The absolute 0.5 threshold is unreachable on this domain.** With the
   checkpoint's JevBench-fitted temperature calibration, P(bird) tops out at
   0.274 across 230 frames. This matches the noul bias documented for the
   OmniJev family (`system_one_detector/README.md`) plus domain shift: JevBench
   is not camera-trap footage. A 0.5-cut COCO export is empty by construction.
2. **Ranking signal is unverified.** The top-ranked frame
   (`IMG_0572_frame_000700`, 0.274) contains a dark ground shape a human can
   misread as a bird; the site owner judges all four top frames bird-free. If
   that holds, the model's *negatives* were correct and even its ranking may be
   surfacing texture, not birds. Without gold labels, neither recall nor
   ranking quality can be claimed — which is itself the finding.
3. **Consequence for pseudo-labeling:** do not threshold this checkpoint on
   H55 as-is. Either (a) annotate a small gold set (100–200 frames) and fit a
   threshold / recalibration on camera-trap data, (b) use score ranking per
   video to surface candidate frames for review, or (c) cross-check with the
   repo's h23-trained YOLO/RT-DETR adapters, which were fine-tuned on this
   domain.
4. **The drawn boxes show localization is not there yet.** Rendering the four
   0.2-threshold annotations (`tools/coco_draw.py`,
   `viz_poc_h55_70tok_coco_t020/`): all four boxes sit on vegetation texture,
   and all four come from a single video (`IMG_0572`), so nothing here is
   independent evidence.

## Decisions and next steps (2026-10-04)

1. **Gold labels are coming.** Researchers hand-annotated a subset of H55
   frames with bird presence (a mix of positive and negative frames). When
   downloaded, this becomes the first true evaluation set for the System One
   questions on camera-trap data, and the basis for threshold fitting.
2. **Exploit temporal structure.** Frames are stride-10 samples of videos; a
   bird present for 2 s spans ~60 extracted-frame-neighbours. Plan: aggregate
   decisions per video (max / median noul across a video's frames) and evaluate
   the aggregation against per-frame gold. Presence labels only — the cell
   question stays untrainable until location boxes arrive.
3. **The Browning info bar stays.** It is constant across frames, so its
   systematic effect is absorbable: temperature/threshold fitting absorbs part;
   a retrained decision head can treat it as context rather than noise. No
   cropping.
4. **Fine-tuning roadmap** (see "Jev-Omni architecture" below for what the
   model is):
   - Tier 1 — refit temperature + fit an operating threshold on gold frames
     (no training, hours).
   - Tier 2 — retrain the decision head on frozen features: `omni_mlx/
     classifier.py` already extracts the LM's last hidden state, and the head
     is a linear probe (`(hidden - mu)/sd @ W^T + b`, sliced to the option
     count). Measured locally: `linear.weight` is **256×3840**, plus `mu`/`sd`
     (1×3840) and bias — **990,976 FP32 params total**. The 4-bit backbone
     stays frozen, and training on 4-bit-extracted features exactly matches
     the serving path. Head training is a logistic-regression-scale job on
     this Mac; needs hidden-state capture wiring in the POC first.
   - Tier 3 — LoRA on the backbone. The upstream fine-tune recipe ships
     inside `decision_config.json` (see below). Requires the upstream BF16
     checkpoint and CUDA (PACE); the local 4-bit MLX conversion is an
     inference artifact, not a training starting point. mlx-vlm 0.7.4 also
     ships an SFT/LoRA trainer with a vision-language loss and a
     `gemma4_unified` model implementation — training support on Apple
     Silicon is plausible but untested for this architecture.

### Jev-Omni architecture (what "System One" is under the hood)

From the local checkpoint (`models/Jev-Omni-MLX-4bit/`) and the upstream
`akhilaaa3/Jev-Omni` artifact:

- **Base**: `google/gemma-4-12B-it` (HF `base_model` tag), 48-layer text
  backbone, hidden 3840, with vision and audio towers
  (`Gemma4UnifiedForConditionalGeneration`). Jev-Omni is tagged `merged` —
  it **is** a fine-tune: "Built on Gemma 4 12B IT, with a 30,000-question
  fine-tuning run" (upstream README).
- **Decision head**: prompt(state + question + options) → one forward pass →
  last-token hidden state → normalize with stored `mu`/`sd` → linear
  3840→256 → slice to the option count → softmax → JevBench temperature
  (T=1.11517). No token generation. The head is FP32 even in the 4-bit MLX
  conversion; vision weights stayed BF16.
- **The upstream fine-tuning recipe is public**, embedded in
  `decision_config.json`: LoRA rank 512, alpha 512, lr 1e-05 (head too),
  24,000 records, 1 epoch, 750 steps, effective batch 32, 4-GPU DDP, ~2.1B
  trainable params, initialized from "FP32 merged trained v1 + trained head +
  fresh LoRA" — i.e. iterative merge-then-LoRA rounds. The artifact is
  Apache-2.0 (base under Gemma terms).
- **Ecosystem proof the recipe generalizes**: OmniJev v1.1 (tinnel123) is the
  same design on Qwen3.5 backbones in three sizes — LoRA + decision heads +
  ordinal head, with a per-checkpoint `noul` bias shipped in its release
  manifest (fine-tuned heads shift decision boundaries; calibration artifacts
  must travel with the weights).

So: yes, a VLM, and yes, fine-tunable — the artifact itself is the output of
exactly the process the user hypothesized. Head-only training runs here;
LoRA-class training needs the BF16 upstream and GPUs (or an untested mlx-vlm
SFT path on Apple Silicon).

## Caveats

- **No gold labels for H55.** Nothing here measures accuracy; agreement and
  confidence only.
- **The Browning info bar is part of the pixels.** Every frame carries a burned
  -in footer (temperature, site `H55`, timestamp, logo). Vision backends see it
  and may read it; the same strip occupies the bottom third's lower edge, so
  cell answers like `bc`/`bl`/`br` can be attracted to the overlay. A crop of
  the footer (~last 40 px) is a worthwhile ablation before trusting bottom-row
  cells.
- **Site mismatch in the text state.** `datasets/questions.py:text_state` says
  "freeman camera trap" for every frame, but the H55 overlay stamps `H55`.
  Harmless for pixel-seeing backends, but it means text-only baselines (Jev,
  Laya) would be fed the wrong site label on this data.
- The MLX checkpoint is a third-party 4-bit quantization with its own head and
  JevBench-fitted calibration; its published 85.90% is on JevBench, not camera
  traps. The 4-bit conversion may behave differently from the fp16 CUDA loader.
- The POC's cell question has **9 options** (no `none`) — emptiness is handled
  by the `bird_present` gate. The engine question bank has 10 options including
  `none`; the converter accepts either shape.
- Sampling is by video, not by frame, so all frames of a clip share a scene —
  treat frame counts as correlated, not independent evidence.
- `frame_map.csv`'s original indices make temporal ordering recoverable
  (`_frame_%06d`), which plain PNG folders usually lose.

## Reproduce

```bash
# 1. sample
python3 -m system_one_detector.tools.sample_videos \
    --video-dir data/H55/Download1_28072024 --num 5 --seed 42 \
    --output data/H55/video_sample.json
# 2. frames
python3 -m system_one_detector.tools.video_to_frames \
    --sample-json data/H55/video_sample.json \
    --out-dir data/H55/frames_sample5_stride10 --stride 10
# 3. dry-run plumbing check
python3 -m system_one_detector.main system_one_detector/configs/h55_sample.yaml --dry-run
# 4. real model (Mac + MLX)
.venv-jevomni/bin/python system_one_detector/jev_omni_mlx_poc.py \
    --images data/H55/frames_sample5_stride10 --no-browser \
    --json outputs/h55/poc_h55_70tok.json
# 5. COCO
python3 -m system_one_detector.tools.coco_from_decisions \
    --input outputs/h55/poc_h55_70tok.json \
    --frames-dir data/H55/frames_sample5_stride10 \
    --output outputs/h55/poc_h55_70tok_coco.json
# 6. draw the boxes back onto the frames (+ montage)
python3 -m system_one_detector.tools.coco_draw \
    --coco outputs/h55/poc_h55_70tok_coco_t020.json \
    --images-dir data/H55/frames_sample5_stride10
```

For a pixel-seeing API backend instead of the local MLX model, point a config
at the same frames dir — e.g. Clef (`configs/clef_h23.yaml` pattern, needs
`CLOUDFLARE_ACCOUNT_ID`/`CLOUDFLARE_AUTH_TOKEN`) or a OneJev-style
`/v1/systemone` server with `send_media: true` — and convert its
`decisions.json` with the same step 5.
